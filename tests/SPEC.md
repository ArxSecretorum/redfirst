# ТЗ: регрессионный набор redfirst

Составлено 2026-08-17 после трёх состязательных прогонов, которые нашли около
девяноста дефектов. Набор существует, чтобы найденное не возвращалось, и чтобы
следующий прогон не тратился на уже закрытое.

## Ц0. Чего набор НЕ делает

Не находит новые дефекты. Ловит только возврат старых. Состязательные прогоны
он не заменяет — он делает их дешевле.

## Ц1. Направление важнее результата

Каждый случай объявляет, чего он ждёт:

* `red` — инструмент **обязан** поднять тревогу (ненулевой код, нужная строка).
  Провал такого случая = инструмент прозевал дефект = **блокер**.
* `green` — инструмент **обязан** промолчать. Провал = заругался зря = **шум**.

Сводка считает их раздельно. «3 упало» ничего не говорит; «1 блокер, 2 шума» —
говорит всё. Ложное зелёное — единственный класс, ради которого набор написан.

## Ц2. Две оболочки обязательны

Каждый случай гоняется в `dash` и в `bash`. Расхождение между ними — отдельный
класс отказа (`SHELL-DIFF`). Обоснование: `$((10#08))` — расширение bash, в dash
синтаксическая ошибка; баг был невидим в bash и валил `due` на любой дате
августа. `/bin/sh` на Debian и Raspberry Pi OS — это dash.

Если dash не установлен — печатать предупреждение и продолжать в одной
оболочке. Молча пропускать нельзя.

## Ц3. Набор обязан уметь падать

Режим `run --self-check`: раннер выключает правила инструмента через
`REDFIRST_BREAK=<имя>` и проверяет, что набор **краснеет**. Если при сломанном
инструменте набор зелёный — раннер выходит с кодом 3 и сообщает, что доверять
ему нельзя.

Без этого получится зелёный набор, который ничего не доказывает, — та же
«зелёное ничего не значит», этажом выше.

## Ц4. Происхождение у каждого случая

Поле `дата: описание дефекта`. Набор одновременно журнал инцидентов.

## Ц5. Золотой корпус на настоящем коде

Часть случаев работает не на синтетике, а на копиях реальных файлов с вердиктом,
проверенным вручную. Синтетические стенды не поймали `selectionTier` —
поймал живой ArxRemote.

Файлы в корпусе обезличены: без имён продуктов, путей владельца, хостов.

## Ц6. Открытый дефект — не зелёный и не регрессия

Известный незакрытый дефект помечается прямо в случае (`red?`, `green?`). Такой
случай не проходит и не должен проходить, но он не блокер: блокер — это то, что
СЛОМАЛОСЬ, а здесь ничего не ломалось.

Различие нужно ровно для одного: чтобы набор, в котором лежат случаи на ещё не
починенные дефекты, продолжал ловить новые регрессии. Без пометки он красный
навсегда и в этот момент перестаёт быть регрессионным набором.

Пометка не должна стать способом спрятать красное:

* открытые дефекты печатаются поимённо в каждом прогоне;
* код возврата никогда не `0`, пока открыт хоть один;
* помеченный случай, который **прошёл**, — отдельный класс отказа с кодом `2`.
  Устаревшая пометка хуже дефекта: она навсегда глушит уже работающую проверку.

# Устройство

```
tests/
  SPEC.md            этот документ
  run                раннер, POSIX sh, без зависимостей
  cases/*.cases      табличные случаи
  cases/<id>/        каталожные случаи (setup.sh + expect)
  unit/*.sh          модульные тесты внутренних функций
  fixtures/          синтетические стенды по языкам
  fixtures/golden/   золотой корпус: обезличенный настоящий код
```

Модульных тестов три: `parse_date`, `split3_and_noise`, `classifier`. Последний
стал возможен только после того, как awk-программа переехала из строки внутри
`cmd_wired` в переменную `CLASSIFIER`.

## Ф1. Формат табличного случая

Одна строка, поля через `~`, пробелы вокруг обрезаются:

```
id ~ напр ~ код ~ подстрока ~ стенд ~ команда ~ происхождение
```

* `id` — уникальный, латиницей, через дефис.
* `напр` — `red` или `green`; с суффиксом `?` — то же направление плюс
  «сегодня не выполняется, дефект открыт» (Ц6).
* `код` — ожидаемый код возврата, либо `*` если не важен.
* `подстрока` — одно или несколько утверждений через `&&`; `-` если не важна.
* `стенд` — `@имя` каталога из `fixtures/`, либо `-` (пустой проект),
  либо `reg:<содержимое>` для реестра активов (`\n` разворачивается).
* `команда` — аргументы после `redfirst`, либо `NOARGS`, либо `@sh <код>`.
* `происхождение` — дата и одна фраза.

Строки, начинающиеся с `#`, и пустые пропускаются.

### Ф1.1. Виды утверждений

| запись | что проверяет |
|---|---|
| `текст` | подстрока есть в объединённом выводе |
| `!текст` | подстроки НЕТ нигде в выводе |
| `out:текст` | подстрока есть именно в STDOUT |
| `err:текст` | подстрока есть именно в STDERR |
| `n:<корзина>=<число>` | точное число в корзине отчёта `wired` |
| `sum` | арифметика отчёта сходится |

Корзины: `files` (файлов с упоминанием), `code` (из них имеют упоминание в
коде), `text` (только вне кода), `hits` (упоминаний в коде всего).

`sum` требует `files = code + text`. Он существует потому, что отчёт «всего
совпадений 4» при нулях по всем корзинам проходил проверку подстрокой и выдавал
категоричный вердикт на пустой классификации.

Число берётся только из строк самого отчёта — тех, что начинаются с двух
пробелов. Без этой привязки парсер вытащил число из прозы под отчётом, где
случайно стояли те же слова.

### Ф1.2. Команда `@sh`

`@sh <код>` выполняет код в стенде вместо запуска подкоманды. Доступны `$RF`
(путь к `bin/redfirst`), `$INSTALL` (`install.sh`), `$RFROOT` (корень репозитория).
Нужна там, где проверяемое — не подкоманда: установщик, повторный запуск,
чтение получившегося файла вместо рапорта о нём.

## Ц7. Не проверено — не пройдено

Инструмент имеет три исхода потому, что «проверить не удалось» ≠ «всё в
порядке». У набора до 2026-08-17 исходов было четыре — ok, блокер, шум,
известный дефект, — и случай, чьё условие на этой платформе не создаётся,
засчитывался **пройденным**. Тот же паттерн, против которого написан
инструмент, этажом выше.

Пятый исход: **НЕ ПРОВЕРЕНО**. Условие объявляет не платформа и не догадка о
ней, а сам `setup.sh`: он пытается создать нужное состояние, **проверяет, что
создалось**, и только тогда продолжает. Не создалось — печатает причину и
выходит кодом 77.

Пропуски перечисляются поимённо в каждом прогоне, и слово «Чисто» в отчёте
становится недоступно: код возврата отвечает на вопрос «что-нибудь сломалось»,
а эта строка — на вопрос «всё ли проверено». Код при этом не меняется — тот же
приём, что и с отсутствующим dash: недоступное измерение объявляется громко и
не выдаётся за провал.

## Ф2. Каталожный случай

`cases/<id>/setup.sh` готовит каталог, `cases/<id>/expect` содержит те же поля,
кроме `id` (он равен имени каталога) и `стенд` (им и является `setup.sh`):

```
напр ~ код ~ подстрока ~ команда ~ происхождение
```

Для того, что не помещается в одну строку: многострочные литералы, heredoc,
YAML-блоки, PEM, CP1251, пути с пробелами и кириллицей.

`setup.sh` может выйти кодом **77** — «условие здесь не создаётся» (Ц7).
Первая напечатанная им строка становится причиной в отчёте. Проверять, что
условие создалось, обязан сам скрипт: `chmod 000` под Git Bash на Windows
молча не действует, и случай, доверившийся ему, засчитался бы пройденным.

## Ф3. Модульный тест

`unit/<имя>.sh` подключает инструмент как библиотеку и проверяет внутренние
функции напрямую. Для этого в `bin/redfirst` диспетчер запускается только когда
`REDFIRST_LIB` не выставлен.

## Ф4. Точки слома для самопроверки

`REDFIRST_BREAK` понимает значения, каждое отключает одно свойство:

| значение | что ломает | какой случай обязан покраснеть |
|---|---|---|
| `dates` | принимать любую дату как валидную | битые даты в `due` |
| `noise` | не отсеивать тестовые каталоги | вызов только из теста |
| `single` | сдвинуть порог одного файла | мёртвый символ |
| `quiet` | печатать в stdout вместо stderr | видимость хука |
| `strings` | не вычищать строки и комментарии | символ только в строке |

До 2026-08-17 вместо `single` стоял `decl` — он ломал распознавание объявления.
Распознавания больше нет, ломать нечего; порог «один файл против нескольких»
занял его место как единственное оставшееся решающее правило.

Переменная читается только когда выставлена `REDFIRST_SELFTEST=1`, чтобы её
нельзя было включить случайно в бою.

## Ф5. Вывод раннера

```
redfirst tests: оболочки: dash bash

  БЛОКЕРЫ (инструмент прозевал дефект)   0
  ШУМ (заругался зря)                    0
  РАСХОЖДЕНИЯ ОБОЛОЧЕК                   0
  ИЗВЕСТНЫЕ ОТКРЫТЫЕ ДЕФЕКТЫ             0
  НЕ ПРОВЕРЕНО (условие не создалось)    4
  пройдено                               208 из 212

НЕ ПРОВЕРЕНО:
  unreadable-registry (dash): chmod 000 не действует в этой среде

```

Код возврата:

| код | когда |
|---|---|
| `0` | чисто, ни одного открытого дефекта |
| `1` | шум и/или открытые известные дефекты; регрессий нет |
| `2` | блокеры, расхождения оболочек **или устаревшая пометка `?`** |
| `3` | самопроверка провалилась, набору доверять нельзя |

# План работ

1. **Библиотечный режим** — одна строка в `bin/redfirst`, чтобы функции можно
   было вызывать из тестов.
2. **Точки слома** — четыре ветки `REDFIRST_BREAK`, каждая за проверкой
   `REDFIRST_SELFTEST`.
3. **Раннер** — разбор случаев, две оболочки, подсчёт по классам, самопроверка.
4. **Табличные случаи** — перенос дефектов трёх прогонов: `due`, `verified`,
   `wired`, `samples`, `counter`, установщик.
5. **Каталожные случаи** — многострочное и с файлами.
6. **Модульные** — `parse_date` (границы, високосные), `split3` (юникод, табы,
   лишние разделители), `is_noise` (AUDIT против PaymentIT, `bin/` Cargo).
7. **Золотой корпус** — обезличенные копии реальных файлов, вердикт вручную.
8. **Прогон, починка найденного, повтор до зелёного.**
9. **README** — раздел о том, как гонять набор.

# Критерий готовности первой версии — выполнен 2026-08-17

Ниже состояние на момент, когда набор только появился. Действующие числа — в
разделе «Критерий готовности расширения» в конце документа: с появлением
случаев на незакрытые блокеры код возврата стал `1`, и это правильно.

* `sh tests/run` завершается кодом 0: **128 из 128**, dash и bash.
* `sh tests/run --self-check` подтверждает, что набор краснеет по каждой из
  четырёх точек слома.
* Время на целевой платформе (Raspberry Pi OS, dash): полный прогон **2,8 с**,
  самопроверка **0,47 с**. Под Git Bash на Windows — 77 с и 25 с
  соответственно; разница целиком в цене порождения процессов, а не в наборе.
* Каждый дефект, воспроизведённый вручную по итогам трёх прогонов, имеет свой
  случай с датой и описанием.

## Что набор нашёл в себе самом

Первый же прогон дал десять расхождений, и два из них были ошибками **в
ожиданиях теста**, а не в инструменте: я неверно посчитал число дней до
2000-02-29 и 2100-02-28. Ещё два случая были составлены неверно — сентябрьская
дата 2026 года лежит в будущем, а `AUDIT` никто не вызывает, так что мёртв он
справедливо.

Самопроверка нашла дыру, которую не видел ни один из трёх состязательных
прогонов: раннер сливал stdout и stderr, поэтому **ни один случай не проверял,
куда именно идёт вывод** — а от этого зависит, доходит ли до человека хук.
Отсюда префиксы `err:` и `out:` в подстроках.

И разбор строк случая стоил двенадцати процессов на строку — двадцать одна
секунда на двух случаях. Та же ошибка, что была в `due`, повторённая в его
собственной оснастке.

# Наблюдение о среде (2026-08-17)

Сборка dash под Git Bash на Windows коверкает кириллицу в heredoc-блоках
(`cat <<'EOF'`), но не в `printf`. На настоящем Linux dash — проверено на
Raspberry Pi OS — вывод корректен. Это артефакт среды разработки, не дефект
инструмента.

Практическое следствие: подстроки в случаях лучше брать ASCII там, где это
возможно, — имена команд, числа, коды. Кириллические подстроки работают, но
не в проверках вывода `usage`.

# ТЗ: расширение каркаса (2026-08-17, вторая половина дня)

Набор из 64 случаев зелёный и этим опасен: он проверяет то, что инструмент уже
умеет, и молчит о трёх блокерах публикации, которые известны поимённо. Каркас
расширяется, чтобы блокеры можно было **выразить** — сейчас язык случаев для
них слишком беден, — и чтобы корпус перестал быть синтетическим.

Порядок пунктов — от возможностей каркаса к случаям: случай нельзя написать
раньше, чем появится язык, на котором его записать.

## Р1. Несколько утверждений в одном случае

Поле `подстрока` разбирается на части по `&&`; каждая проверяется отдельно, со
своим префиксом. Первая непройденная называется в отчёте.

Зачем: одному отчёту нужно предъявлять несколько требований сразу — число в
корзине И сходимость арифметики. Заводить на каждое утверждение отдельный
случай — значит гонять инструмент заново ради одной строки вывода, а полный
прогон под Windows уже стоит 77 с.

Заодно: `trim_var` и `split_fields` перестают форкать. Шесть подоболочек на
строку случая — та же ошибка, что была в `due` и в первой версии раннера,
повторённая третий раз.

## Р2. Структурные проверки отчёта

Долг 6 из handoff: раннер сверяет подстроку, а не структуру, поэтому отчёт
«всего совпадений 4», где по всем корзинам нули, проходит незамеченным.

Два новых префикса:

* `n:<корзина>=<число>` — точное число. Корзины: `total`, `decl`, `text`,
  `imp`, `call` (имена латиницей — они внутренние, кириллица только в выводе).
* `sum` — арифметика сходится: `total = decl + text + imp + call`.

Проверка ищет числа в отчёте `wired` по его собственным подписям. Если подпись
не найдена — это провал случая с показом того, что было прочитано, а не тихий
пропуск.

## Р3. Каталожные случаи

Долг 3: формат объявлен в Ф2 и не реализован ни одним случаем. `cases/<id>/setup.sh`
готовит каталог, `cases/<id>/expect` содержит те же поля, кроме `стенд`. `id`
берётся из имени каталога.

Без этого недоступны: многострочные литералы (docstring, raw-строки Kotlin,
YAML-блоки, PEM), CP1251, пути с пробелами и кириллицей. Ровно то, на чём стоят
блокеры 2 и 3.

## Р4. Произвольная команда `@sh`

Поле `команда` со значением `@sh <код>` выполняет код в стенде; доступны `$RF`
(путь к `bin/redfirst`), `$INSTALL` (`install.sh`), `$ROOT`.

Зачем: установщик запускается не как подкоманда инструмента, а идемпотентность
проверяется только повторным запуском. Без этой формы Р9 невыразим.

## Р5. Пометка «известный открытый дефект»

`напр` принимает `red?` и `green?` — то же направление плюс «сегодня не
выполняется, дефект открыт».

Зачем: случаи на три блокера пишутся **до** починки. Без пометки набор
становится навсегда красным и в этот момент перестаёт отличать известный дефект
от новой регрессии — то есть перестаёт быть регрессионным набором.

Пометка не должна стать способом спрятать красное, поэтому она громкая:

* открытые дефекты печатаются поимённо в каждом прогоне;
* код возврата `1`, никогда `0`. Пока дефект открыт, «чисто» невозможно;
* случай с пометкой, который **прошёл**, — это код `2` и требование снять
  пометку. Устаревшая пометка опаснее самого дефекта: она глушит уже
  починенную проверку навсегда.

## Р6. Пятая точка слома — `strings`

Долг 4: `REDFIRST_BREAK` ломает даты, шум, объявления и поток вывода. Классификатор
строк и комментариев — самая сложная часть инструмента (awk на 45 строк) — не
проверен ни одной точкой. Значение `strings` отключает вычистку строк и
комментариев; покраснеть обязаны случаи, где символ упомянут только в строке.

## Р7. Золотой корпус на настоящем коде

Долг 1: синтетика не поймала `selectionTier` — поймал живой ArxRemote.

Обезличенные копии реальных файлов, вердикт проверен глазами:

| символ | правда | инструмент сегодня |
|---|---|---|
| `selectionTier` | мёртв | **жив** — ложное зелёное |
| `identityFingerprintSha256` | жив | **мёртв** — ложное красное |
| `DiagnosticRingLog` | мёртв | мёртв ✓ контроль |
| `PlaybackService` | жив | жив ✓ контроль |

Обезличивание: без имён продуктов, пакетов владельца, хостов и путей. Форма кода
сохраняется дословно — она и есть предмет проверки.

## Р8. Случаи на три блокера

Долг 2, пишутся до починки, с пометкой Р5.

1. **Ложное зелёное на формах объявления.** Строка объявления считается вызовом
   там, где форма не покрыта. Проверить **эмпирически**, а не чтением регулярки:
   Kotlin extension, Java-метод с типом возврата, метод класса без ключевого
   слова, shell-функция `f() {`, Go-метод с получателем.
2. **Многострочные литералы.** `strip_strings` сбрасывает состояние кавычек на
   каждой строке: символ, упомянутый в docstring, засчитывается вызовом, а в
   отчёте стоит «комментарии/строки 0».
3. **Арифметика отчёта** при пробеле в пути и при непарном апострофе.

Каждый случай сопровождается замером Р2: не «в выводе есть слово», а «в корзине
столько-то».

# Замена классификатора — 2026-08-17, вечер

Все двенадцать помеченных случаев были критерием приёмки. Они перевернулись,
пометок в наборе не осталось.

## Решение из handoff проверено на данных и уточнено

Записано было так: «не чинить эвристику имя-значение четвёртый раз, а выбросить
её целиком; считать, в скольких файлах вне тестов встречается символ;
классификатор при этом удаляется, инструмент становится короче».

Правило в чистом виде прогнано по всему корпусу — 29 символов с вердиктом,
проверенным глазами:

| исход | сколько |
|---|---|
| правило право, включая оба ложных вердикта золотого корпуса | 22 |
| «жив», а на деле мёртв | 4 |
| «мёртв», а на деле жив — третий исход handoff | 3 |

Четыре ошибки в опасную сторону — один класс: **символ упомянут во втором файле
только в строке или в комментарии.** Выбросить вместе с эвристикой ещё и
вычистку строк значит отдать за шесть форм ложного зелёного четыре случая
тихого «всё в порядке» — обмен в запрещённую сторону.

Поэтому выброшено ровно то, что провалилось: `is_decl_re` и `DECL_KEYWORDS`,
распознавание объявления по синтаксису. Вычистка строк и комментариев осталась
и была починена.

## Что теперь делает классификатор

Один проход слева направо, состояние переносится между строками. Строки и
комментарии разбираются в одном сканировании, потому что по отдельности оба
разбора неверны: `//` внутри строки — не комментарий, апостроф внутри
комментария — не строка.

* **Многострочный литерал.** Тройная кавычка и обратный апостроф спанят строки;
  одиночная кавычка — нет. Прежний сброс на каждой строке засчитывал прозу
  docstring вызовами; перенос без ограничения на одиночную кавычку гасил бы
  остаток файла после `don't` в комментарии.
* **Интерполяция.** Содержимое `${…}` внутри строки — код. Оба вызова
  `identityFingerprintSha256` в настоящем проекте стоят внутри шаблонов строк,
  и вычистка объявляла живой символ мёртвым.
* **Heredoc** для shell-файлов; `<<` в остальных языках — сдвиг, не heredoc.
* **Импорт** не делает файл использующим.

## Четыре исхода вместо числа

| исход | код | когда |
|---|---|---|
| не встречается вообще | 2 | ноль совпадений — не вывод о мёртвом коде |
| в коде нет нигде | 1 | есть только в строках, комментариях и импортах |
| единственное упоминание | 1 | одно упоминание в коде во всём проекте |
| только внутри своего файла | 1 | несколько упоминаний, все в одном файле |
| живёт | 0 | код нескольких файлов |

Разделение двух средних исходов взято из тех же данных: единственное упоминание
и «несколько, но в одном файле» — разные вещи, и различить их можно счётом, без
разбора синтаксиса.

## Итог по корпусу

30 символов, верно 29. Единственный расход — `DeadThing` в Go: получатель метода
`func (d DeadThing) Method()` даёт второе упоминание в том же файле, и вердикт
смягчается с «единственного» до «только внутри своего файла». Код всё равно 1,
обе строки показаны, конструирования среди них нет.

Свойство, которое держится без исключений: **ни один мёртвый символ в корпусе
не получает код 0.** Ошибки остались только в громкую сторону.

Инструмент **не стал короче**: 673 строки было, 737 стало. Удалено 26 строк
распознавания объявлений, добавлено около девяноста — разборщик строк с
переносом состояния, интерполяция, heredoc, четвёртый исход. Предсказание

# Громкая половина — 2026-08-17, ночь

Прежний набор проверял, что инструмент отвечает верно. Чего он не проверял
совсем: что инструмент **отказывается отвечать**, когда не может. Одиннадцать
таких веток не имели ни одного случая — при том что ради них он и написан.

## Восемь достижимы везде

Пустой проект, имя длиннее двухсот символов, реестр-каталог, занятый замок,
`sources` из одних комментариев, установка в проект с нулём файлов, корень
репозитория выше текущего каталога, обрезанный восемью список. Каждая ветка
перед написанием случая вызвана руками — все восемь срабатывают.

## Три требуют нечитаемого пути, и здесь их не создать

`chmod 000` под Git Bash на Windows **не действует**: файл после него читается.
Случай, доверившийся `chmod`, засчитался бы пройденным, ничего не проверив.
Отсюда исход НЕ ПРОВЕРЕНО (Ц7) и правило: условие проверяет сам `setup.sh`.

Написаны два: нечитаемый реестр и ошибка поиска в `counter`. На Windows оба
пропускаются с названной причиной, на целевой платформе должны выполняться.

**Открытый вопрос, не закрытый догадкой.** Третья ветка — «часть путей не
прочитана» в `counter` — срабатывает, когда grep пишет в stderr, но выходит
кодом не больше единицы. У GNU grep статус при любой ошибке равен двум, и тогда
ветка недостижима, а условием выше её перехватывает «ОШИБКА ПОИСКА». Случай на
неё **не написан**: сначала нужно проверить на Pi, достижима ли она вообще.
Написать тест на предположение о чужом grep — то же самое, что подтвердить
отсутствие, не поискав присутствие.

## Разборщик стал проверяемым

Программа переехала из строки внутри `cmd_wired` в переменную `CLASSIFIER`.
До этого каждое утверждение о ней стоило полного запуска инструмента — полторы
секунды и провал, приходящий косвенно, вердиктом вместо корзины.

`tests/unit/classifier.sh` — **26 утверждений**: экранированная кавычка,
вложенная интерполяция, многострочный шаблон JS с интерполяцией и без, heredoc
обычный, с дефисом и в кавычках, возврат к коду после терминатора, сдвиг `<<`
в не-shell, блочный комментарий на несколько строк, код после его закрытия,
хвостовой комментарий, решётка внутри строки Python, `--` в SQL, решётка в
Kotlin комментарием не являющаяся, тройные кавычки обоих видов, непарный
апостроф, импорт против вызова.

Все двадцать шесть прошли с первого прогона — значит это было покрытие, а не
дефекты. Проверено, что набор умеет краснеть: три поломки разборщика по
очереди, каждая называет ровно те утверждения, которые её держат.
